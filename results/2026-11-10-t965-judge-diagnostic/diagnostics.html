01 / Finding

Two issues, not one universal cause.

The code window contains active highlights outside the before-K pattern. The other two windows fit the pattern at every highlighted token, yet the judge’s answers depend on how the example is presented.

Seeing K is necessary for some rescues, but it does not guarantee reliable classification. These tests diagnose the judge and the explanation’s coverage; they do not establish the MOLT’s complete function.

04 / What we learned

Read each failure separately

Development → Kit

Both highlights fit the pattern. A single highlight still gets 0, even after removing the few-shots. But the literal task and the short excerpt both get 1.

Supported: the judge can recognize this pattern; failure depends on context and task framing. We have not isolated which part of the long context or explanation is responsible.

Ton / ton → katsu

Every original highlight precedes k. Removing only the first two pairs of highlight markers changes 0 to 1 without changing the underlying passage text.

Supported: the marking configuration affects this judgment. The short example still gets 0, so shortening text is not a universal fix.

.wait → key

The comma and plus are genuinely active, but both precede h. A before-K rule does not fully explain this window. Keeping only .wait gives 1 with the original few-shots.

Supported: coverage of the explanation matters. Removing the few-shots or using the literal single-highlight task still gives 0, revealing additional judge sensitivity.

A correction to the earlier summary. The seven-window “before-K” subset was selected by its final activation peak. That did not guarantee every earlier highlighted token also preceded K. Six of the seven windows satisfy that stronger condition; four of those six are accepted with the revised explanation and continuation.
